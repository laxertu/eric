Persistence#

Base classes for channels and connections repositories. The main idea is that a repository relies on some KV storage engine abstraction, and uses it for storing its own configuration, and its correspondant composites repositories to build final objects to return.

To build a persistence layer is needed to provide an implementation to some of above abstractions, and use them to build a custom ChannelRepository

Here is a possible Redis implementation

Suggestions

If your implementation uses objects that are directly persistable by storage engine you are using, cleanest manner of implementing your custom layer is to simply give an implementation to a KvStorage and just use it in all composite repositories. Otherwise you should implement a dump strategy inside repositories themselves. An example is RedisQueues persistence, as Redis client used is not serializable by pickle.

Builder#

ChannelRepositoryBuilder is the easiest way to get a working persistence layer. By default it stores everything in one storage instance, each kind of object under its own namespace:

from eric_sse.builder import ChannelRepositoryBuilder

repository = ChannelRepositoryBuilder(my_storage).listeners(MyListener).build()

channel = repository.create({'retry_timeout_milliseconds': 100})
listener = channel.add_listener()
repository.persist(channel)

Persistence is always explicit: channels and their connections are stored when you call persist. Messages are persisted by queues themselves, so dispatch and broadcast do not need a persist.

class ChannelRepositoryBuilder#

Wires a channel repository and its connections, listeners and queues repositories.

Every part is stored in storage under its own namespace (channel:, connection:, listener:, queue:), unless a dedicated storage or repository is given for it. Each method returns the builder, so calls can be chained:

repository = (
    ChannelRepositoryBuilder(storage)
    .listeners(MyListener)
    .queues_repository(RedisQueuesRepository(redis_connection))
    .build()
)

Channels built by the resulting repository create their listeners and queues through it. Nothing is persisted implicitly: call the repository’s persist when needed.

When a part is configured more than once, the last call wins.

class KvQueueRepository#

Bases: QueueRepositoryInterface, Generic[Q]

Queue repository backed by a KvStorage.

Queues are stored as they are, keyed by connection id; serialization, if needed, is up to the storage.

Each queue class decides what of its state is serialised. A durable queue keeps its messages in its own backend and serialises only its identity and configuration (e.g. through __getstate__), because messages are written by the queue itself on every push and pop. InMemoryQueue can’t be serialised: use it with a storage that keeps objects in process, such as InMemoryStorage.
